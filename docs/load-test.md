## Findings and fixes (D17.1, first run 2026-10-29)

The first runs failed far above the 0.1 % threshold; both causes were real bugs that only show on PostgreSQL or
under concurrency (H2 and the sequential e2e tests never hit them). Fixed, each guarded by `LoadPathsPostgresIT`
(PostgreSQL 17 Testcontainer, e2e profile, seed data):

| Symptom | Cause | Fix | Test |
|---|---|---|---|
| `GET /api/stores/{id}/pickups` 500 for ~20 % of calls | `Instant.MAX` bound as a query parameter; PostgreSQL rejects it ("timestamp out of range"), H2 accepted it | open end `PickupScheduleService.OPEN_END` = 9999-12-31 | `loadTestReadPathAnswers200` (`/api/stores/{store}/pickups`) |
| Concurrent logins of one user: all but one 409 `CONCURRENT_MODIFICATION` (two devices or tabs logging in at the same moment) | `UserService.markLoggedIn` changed the managed `User`, so `user_account.version` was bumped and the parallel transaction lost the optimistic lock | bulk `update User set lastLoginAt` (`UserRepository.markLoggedIn`), no version bump | `concurrentLoginsOfOneUserAllSucceed` (8 parallel logins) |

No endpoint missed the p95 budget, so no index or cache was added for latency: the hot list queries already use
their indexes (`IndexUsagePostgresIT`), and the slowest paths are `/api/auth/session` and `/api/onboarding/journey`
(p95 about 30 ms) because the journey is computed per request (40-50 Hibernate statements, a constant number of
per-kind queries, not per row). `QueryCountIT` now carries statement budgets for every load-test read path, so an
N+1 regression fails the build before it shows up here.

The 5 failed requests of 59 703 (0.01 %) are `dial: i/o timeout` between the k6 container and the host
(Docker Desktop port forwarding under 100 VUs, status 0), not application errors: the app log has no error for them.

This run measured commit `5ba5be3` plus the two fixes above (before the per-IP limit of `/api/public/**` existed;
the e2e profile switches that limit off, so later runs measure the same thing).
